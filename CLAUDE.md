# TW-Base-Fields — contexte projet pour Claude

> **Avant toute tâche sur ce plugin, consulter d'abord le `CLAUDE.md` du workspace** (`../CLAUDE.md`) et ses `guides/` : outillage de dev commun (pnpm, `dev.cjs`/HMR, Ctrl+C, git push), pièges PowerShell/Windows, `publishFilter`, conventions de nommage/i18n, symlink. Ci-dessous : uniquement le spécifique à TW-Base-Fields.

## Ce que c'est
Plugin TiddlyWiki (`$:/plugins/nikorion/base-fields`) : 10 champs ajoutés au template d'édition, en lignes pleine largeur autour des lignes du core. Aucun JS : wikitext + CSS. **Aucune surcharge de tiddler core** — sections `$:/tags/EditTemplate` placées par `list-before`/`list-after`.

Trois docs, trois publics, **zéro duplication entre eux** : readme du plugin (`src/base-fields/language/<lang>/readme.tid`) = utilisateur du wiki (usage, pas d'interne) ; `README.md` = développeur qui modifie le plugin (installation dev, structure des sources, fonctionnement, recettes d'extension, montée de version TW) ; ce fichier = instructions au modèle (décisions à ne pas défaire, pièges vécus). **Avant de chercher quel fichier toucher, ou d'ajouter une valeur de vocabulaire ou un champ → lire `README.md`** (§ Source layout, § Extending) — ne pas agir de mémoire. Toute info nouvelle va dans le seul document de son public.

## Les 3 lignes ajoutées
Une ligne = un `<div class="bf-extra-row bf-…">` ; chaque contrôle vocabulaire (`role`/`maturity`/`status`/`lifecycle`/`needs`) et chaque champ à valeur unique (`project`/`epistemology`) = un `<span class="bf-edit-field">` contenant un libellé `<em class="tc-edit tc-small-gap-right">` (transclusion de `Fields/<champ>/Prompt` ; infobulle facultative `Fields/<champ>/Prompt/Hint` en `title` du `<em>`, champs à valeur unique seulement, aujourd'hui `epistemology` — celle d'un contrôle rouge est portée par le `span.bf-edit-field` englobant), le contrôle, puis `bf-delete-field-button`. Exception : les champs liste (`technology`/`equipment`/`disciplines`), `<span class="bf-list-field">`, n'ont pas de libellé visible — leur placeholder en tient lieu, comme pour l'ex-`tools`.

`bf-list-value-field(field)` (champs liste : pastilles + saisie comme les tags) et `bf-single-value-field(field)` (valeur unique : saisie + menu des valeurs déjà utilisées, comme le cœur Type) sont **génériques** : le nom du champ est un paramètre, tiddlers d'état/clés de langue/filtre de complétion en sont tous dérivés — pas de procédure dupliquée par champ.

| Ligne (classe) | Champs (ordre) | Section | Macros |
|---|---|---|---|
| `.bf-pre-tags-extras` | `project`, `epistemology` (uniques), `disciplines` (liste) | `discipline-fields.tid` (`list-before: …/EditTemplate/tags`) | `bf-single-value-field`, `bf-list-value-field`, `bf-list-pill` |
| `.bf-post-tags-extras` | `technology`, `equipment` (listes) | `extra-fields.tid` (`list-after: …/EditTemplate/tags`) | idem |
| `.bf-type-extras` | `role`, `maturity`, `lifecycle`, `needs` (liste), `status` | `vocab-fields.tid` (après `…/EditTemplate/type`) | `bf-select-field`, `bf-needs-field` |

Ordre voulu (2026-09-25) : `project`, `epistemology`, `disciplines`, //tags (core)//, `technology`, `equipment` — d'où la ligne `discipline-fields.tid` placée **avant** les tags (`list-before`) et `extra-fields.tid` **après** (`list-after`), malgré leurs noms de fichier historiques (gardés tels quels pour ne pas casser les renvois du dépôt).

## Spécificités
- **Aucune UI de config des vocabulaires, volontairement** : une valeur ajoutée depuis l'interface ne pourrait pas emporter ses traductions. Ne pas en proposer.
- **`status` n'est affiché que là où il a un sens** — un `role` de `task`/`tasklist`/`routine`, ou aucun rôle — mais **aussi dès que le champ porte une valeur**, quel que soit le rôle. Sans cette seconde condition, un tiddler passé de tâche à autre chose garderait un `status` invisible dans l'éditeur, toujours matché par les filtres et impossible à effacer. La condition de visibilité vit dans le champ `visible-filter` de `vocab/status.tid`, pas dans la section.
- **Chaque `.bf-extra-row` est une ligne pleine largeur**, placée par le seul `list-before`/`list-after` de sa section ; la CSS ne dispose que l'intérieur d'une ligne (flex, `wrap`), rien qui dépende du nesting du formulaire. Ne pas réapparier les blocs avec une ligne du core via une grille sur le conteneur des sections : essayé, abandonné — l'encadré des tags et le bloc `role` partageaient alors une colonne, donc ajouter un tag décalait `role` latéralement, et un encadré de champ liste, à l'étroit, empilait ses pastilles au-dessus de sa saisie.
- **Ne pas réintroduire de surcharge core.** Deux tentatives ont été écartées : copier `$:/core/ui/EditTemplate/type` pour y loger Nature/Statut, et copier `.../tags` pour y loger un champ liste. Une surcharge core fige silencieusement l'ancienne version du tiddler à la montée de version TW (`tags.tid` a d'ailleurs changé entre 5.4.1 et master), et entre en collision avec tout autre plugin touchant la même ligne. Une ligne supplémentaire coûte moins cher.
- **Les saisies des champs liste et valeur unique n'utilisent pas `tag-picker`, et ne doivent pas y revenir.** Cette macro code en dur le placeholder des tags (`$:/language/EditTemplate/Tags/Add/Placeholder`, aucun paramètre pour le changer) et réutilise `newTagNameTiddler`, que `$:/core/ui/EditTemplate` définit une fois pour tout le formulaire : les sélecteurs partageraient alors une saisie, et `save-tiddler-actions` (Ctrl+Entrée) ajouterait le texte en cours comme **tag**. Elles pilotent donc `keyboard-driven-input` directement (la macro sur laquelle `tag-picker` et le champ Type du core sont eux-mêmes bâtis), avec des tiddlers d'état dérivés du nom du champ (`$:/temp/New<Champ>Value*` pour les champs liste, `$:/temp/<champ>/*` pour les champs à valeur unique — voir `bf-list-value-field`/`bf-single-value-field` dans `macros/edit-fields.tid`). Les filtres d'autocomplétion vivent sur `search-filters.tid`, atteints via `configTiddlerFilter` + `firstSearchFilterField`.
- **Les filtres de `search-filters.tid` dédupliquent explicitement** (`each:value[]` pour les champs à valeur unique, `each:list-item[<champ>]` pour les champs liste) — ne pas les simplifier : voir le piège de déduplication dans `../CLAUDE.md`.
- **Après avoir écrit un champ que la saisie affiche, poser `refreshTitle` à `yes`** (vu sur `project`/`epistemology`) : un `$edit-text` ne touche pas un élément qui a le focus, pour ne pas écraser la frappe — sans ça la saisie continue d'afficher le texte tapé alors que le champ vaut autre chose.
- **`<$select default="">` est obligatoire** sur les vocabulaires en liste déroulante (aujourd'hui `role` seul ; `maturity`/`lifecycle`/`status` sont en boutons radio, `radio: yes`) : sans cet attribut le widget assigne `undefined` au nœud DOM quand le champ est absent, aucune option ne correspond (`selectedIndex` = -1) et le contrôle s'affiche vide au lieu de retomber sur l'option placeholder. Cette première option vide doit rester : sans elle, un tiddler sans valeur afficherait la première entrée du vocabulaire comme si elle était choisie. Elle porte `hidden` + `disabled` — invisible dans la liste déroulée (elle ne mène nulle part), toujours affichée par le navigateur dans le contrôle fermé, ce qui est sa seule raison d'être ; vider le champ reste le rôle du bouton.
- **Les valeurs de `role` sont groupées à l'affichage** : champs `groups` (slugs, dans l'ordre) et `group-<slug>` (valeurs) sur `vocab/role.tid`, rendus en `<optgroup>` par `bf-select-field`. Le groupage est purement visuel — le champ ne stocke jamais que le slug de la valeur, les intitulés se traduisent dans `language/<lang>/vocab.multids` (`Vocab/role/Group/<slug>` + `…/Hint` facultatif, posé en infobulle). Une valeur que nul groupe ne réclame (`hub`) est offerte seule, avant le premier intitulé ; un vocabulaire sans champ `groups` (Maturité, Statut) reste une liste plate.
- **Avant une montée de version TW → lire `README.md` § On a TiddlyWiki upgrade** (`bf-list-pill` = copie d'une procédure core à resynchroniser).
- **Couleur de repli d'une pastille : `+[trim[]]` obligatoire** — le texte du tiddler `<champ>-colour.tid` finit par un saut de ligne ; non trimé, `contrastcolour` ne le parse pas, retombe sur `tag-background` (jaune clair) et rend un texte sombre même sur fond foncé, sans erreur (vécu 2026-09-26).
- **Largeur des saisies = longueur du placeholder** (variable CSS `--bf-input-chars`, posée par la macro) : valeur unique = son placeholder (min 12) ; les 3 champs liste partagent le max de leurs placeholders (`bf-list-placeholder-chars`, liste des champs codée dans cette fonction — à compléter si un champ liste s'ajoute).
- **Un libellé s'aligne sur son contrôle en `align-items: baseline`** (lignes Projet/Épistémologie et Rôle/Maturité/Statut), jamais par un `padding-top` : les hauteurs varient d'un contrôle à l'autre — dans un encadré de champ liste, la première ligne est tantôt une pastille, tantôt la saisie (champ vide), 7 px d'écart.
- **`project`, `epistemology` et `disciplines` partagent une ligne, `technology` et `equipment` une autre** — jamais la même : un champ liste prend toute la largeur qu'on lui donne, un libellé en bout de ligne manquerait de place. Ranger un champ de plus dans une de ces deux lignes plutôt qu'en créer une troisième, sauf si l'ordre demandé l'exige (voir le tableau plus haut).
- **Le `$:/config/SyncFilter` du wiki de dev doit exclure les shadows livrés hors du namespace du plugin** (`$:/config/EditTemplateFields/Visibility/`) en plus du préfixe `$:/plugins/nikorion/base-fields/` : sinon un push HMR les fait passer pour des tiddlers modifiés, la synchro les écrit en vrais tiddlers sous `wiki/tiddlers/system/`, et ces copies figées masquent ensuite le plugin. Si ces fichiers réapparaissent : les supprimer, puis vérifier le filtre.
- **Ne jamais conseiller un rechargement d'onglet pour voir une modif** (HMR : il l'annule, cf. `README.md`) ; soit regarder l'onglet ouvert sans y toucher, soit redémarrer TW (`touch src/base-fields/plugin.info`, nodemon reboote) avant de recharger.
- **`maturity` et `needs` sont masqués sur `log`/`decision`/`task`/`tasklist`** (registres datés en ajout seul, tâches portées par `status`), **sauf si le champ est déjà renseigné** — même règle que `status`, dans le `visible-filter` du vocabulaire. Filtre négatif écrit `[<currentTiddler>!role[log]…]`, **pas** `get[role]!match[…]` : sur un tiddler sans rôle, `get[role]` ne renvoie rien et le contrôle serait masqué à tort.
- **`needs` est une liste** : filtrer avec `[contains:needs[verify]]`, jamais `[needs[verify]]` (égalité stricte de la chaîne entière). Son contrôle = une case à cocher par valeur (`$checkbox` en mode `listField`) : cocher ajoute le slug à la liste, décocher le retire, sans toucher aux autres. Pas de `tooltip` sur `$checkbox` : l'infobulle est un `title` sur un `<span>` englobant.
- **Cadre rouge (`.bf-edit-field.bf-stale`)** : un contrôle `maturity`/`status`/`needs` affiché seulement parce que le champ est renseigné (le `visible-filter` du rôle actuel le masquerait) reçoit `stale="yes"` → cadre rouge (`alert-highlight`) autour du libellé + contrôle, et infobulle nommant le rôle (« Les tâches n'utilisent pas ce champ — videz-le »). Le pluriel du rôle vient de `Vocab/role/<slug>/Plural` (fonction `bf-vocab-plural`) ; la phrase = `Fields/Stale/Prefix` + pluriel + `Fields/Stale/Suffix` joints par une espace (un `.multids` **trim** les espaces de bord, d'où le `join[ ]`). Phrase du cadre rouge propre à `status` : `Fields/status/Stale/Hint` (liste des rôles autorisés, **à tenir en phase avec le `visible-filter`** de `vocab/status`). **Sans rôle, `status` renseigné reste affiché, cadré en rouge** comme tout champ incompatible (un rôle effacé après coup laisse un `status` à vider), avec sa propre infobulle `Fields/status/Stale/NoRole/Hint` (« donnez un de ces rôles au tiddler ou videz le champ ») : aucun champ n'est jamais masqué quand il porte une valeur. Ajouter un rôle = ajouter aussi sa clé `/Plural` dans chaque langue. Pièges : `:map` s'applique à **tous** les résultats précédents du run (d'où `plural`/`staleHint` calculés à part dans un `$let`) ; `:and[function…]` ne se déclenche pas comme garde sur une entrée vide : utiliser `:map`.
- **Valeur vide (`blank-value`)** : `maturity` (stub), `lifecycle` (active), `status` (none) — cette valeur **est** le champ vide, jamais stockée ; la choisir supprime le champ. Filtrer avec `[!has[maturity]]`, pas `[maturity[stub]]`. Ne pas réintroduire `default:` ni une valeur « active » stockée.
- **`lifecycle` vide = actif**. Indépendant de `maturity` (une note `stable` peut devenir `obsolete` ou `archived` sans perdre sa maturité).
- **TW-Dynamic-Table consomme ce plugin** (procédures `bf-*`, `blank-value`). **Avant de changer une procédure `bf-*`, un vocabulaire ou d'ajouter un champ → lire `README.md` § Extending** et répercuter dans `../TW-Dynamic-Table` (même tâche, pas plus tard).
- **Tester le rendu hors navigateur** : wiki temporaire (dossier hors repo) dont le `tiddlywiki.info` liste `nikorion/base-fields`, avec `TIDDLYWIKI_PLUGIN_PATH` posé (valeur machine : `../CLAUDE.local.md`), puis `--render`. Envelopper le test dans `<$importvariables filter="[all[shadows+tiddlers]tag[$:/tags/Global]]">` : sans ça les macros/fonctions globales du plugin sont indéfinies et `[function[…]]` renvoie silencieusement tous les tiddlers. Ne pas utiliser `--load` sur le `wiki/` du repo : le syncer y écrit le tiddler de test.
